FlowTex Server Installation Guide

For IT administrators deploying FlowTex on Ubuntu/Debian Linux

1. System Requirements

ResourceMinimumRecommended
CPU2 cores4+ cores (LaTeX compilation is CPU-bound)
RAM4 GB8+ GB (each concurrent compilation uses ~500 MB)
Disk20 GB40+ GB (TeX Live full ~7 GB; LibreOffice + ImageMagick + librsvg ~2 GB; PostgreSQL data + project files + snapshots grow over time)

2. Required Packages

2.1 Node.js 22.x Required

The application server runtime.

# Install Node.js 22 from NodeSource
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo bash -
sudo apt-get install -y nodejs

Verify: node --version should show v22.x.x

2.2 PostgreSQL 16+ Required

All application data (users, projects, files, sessions) is stored in PostgreSQL.

# Install PostgreSQL
sudo apt-get install -y postgresql-16

# Create the database and user
sudo -u postgres createuser --pwprompt flowtex
sudo -u postgres createdb -O flowtex flowtex
Security: Always set a database password in production. Configure it via PGUSER and PGPASSWORD in the .env file.

2.3 TeX Live (Full) Required

The LaTeX compilation engine. A full installation is recommended to ensure all packages users may need are available.

# Full TeX Live installation (includes pdflatex, xelatex, lualatex, latexmk, biber, etc.)
sudo apt-get install -y texlive-full

This installs approximately 7 GB and includes all of the following tools that FlowTex uses:

2.4 Git Required

Used for GitHub repository synchronization (push/pull/clone).

sudo apt-get install -y git

2.5 Build Essentials Required

Some npm packages (e.g., bcrypt) compile native addons during npm install.

sudo apt-get install -y build-essential python3

2.6 DOCX Import Tooling Recommended

FlowTex's DOCX → LaTeX importer converts embedded media so it can be used inside the LaTeX project. If any of these tools is missing, that media format will be skipped (the rest of the import still works).

sudo apt-get install -y librsvg2-bin imagemagick libreoffice
ToolUsed for
rsvg-convert (from librsvg2-bin)SVG figures → PDF (preserves vectors)
convert (ImageMagick)GIF / TIFF / BMP → PNG
soffice (LibreOffice headless)WMF / EMF (legacy Windows metafiles) → PDF
Security: These tools run on attacker-controlled bytes — any authenticated user can upload arbitrary SVG / GIF / TIFF / BMP / WMF / EMF via a DOCX import. FlowTex caps memory / disk / threads on every convert invocation, gates LibreOffice with --safe-mode and a per-invocation UserInstallation dir, and warns at startup if dangerous coders are still enabled — but you must also:
  • Install the hardened ImageMagick policy. The policy lives in the FlowTex source at docs/imagemagick-policy.xml. It disables the historically-RCE-prone coders (PS, EPS, PDF, XPS, MVG, MSL), the network coders (URL, HTTPS, HTTP, FTP), and the Ghostscript delegate, and adds resource caps mirroring our in-process limits. 
    # 1. Back up the existing policy
sudo cp /etc/ImageMagick-7/policy.xml /etc/ImageMagick-7/policy.xml.bak

# 2. Install ours (path to your flowtex checkout)
sudo cp /path/to/flowtex/docs/imagemagick-policy.xml /etc/ImageMagick-7/policy.xml

# 3. Verify — should list rights=none for PS/EPS/PDF/MVG/MSL/URL/HTTPS/...
convert -list policy

# 4. Smoke test — should fail with "not authorized" / "security policy"
printf '%%!PS\n%%%%EOF\n' | convert ps:- /tmp/out.png ; echo exit=$?
    On older systems the path is /etc/ImageMagick-6/policy.xml (same XML works). On macOS Homebrew it's /opt/homebrew/etc/ImageMagick-7/policy.xml. With the policy loaded, the FlowTex boot-time warning (ImageMagick policy.xml does not block …) goes silent.
  • Run the FlowTex process under bwrap or firejail with the project directory bind-mounted read-write and the rest of the filesystem read-only. See SECURITY.md for an example wrapper.
  • Set DISABLE_IMAGE_CONVERSION=1 in .env if you don't need DOCX image conversion. With this flag, FlowTex drops SVG / GIF / TIFF / BMP / WMF / EMF media instead of converting it — the rest of the DOCX import still works.
  • LibreOffice path: the converter looks for soffice at /usr/bin/soffice, /usr/bin/libreoffice, or $PATH. Override with the SOFFICE_BIN environment variable if your install lives elsewhere.

3. Optional Packages

3.1 Redis 7+ Optional

Required only if you plan to run more than one FlowTex server instance behind a load balancer. A single instance handles ~1500 concurrent connections on a 1-vCPU box (verified by the bundled soak harness), so most self-hosted deployments don't need Redis.

What it does: Each FlowTex instance subscribes to one Redis channel (flowtex:ws). When a user on instance A sends a real-time edit / cursor / chat / tracked-change broadcast, the instance publishes the message to that channel. All other instances receive it via the subscription and re-broadcast to their local WS rooms. The publishing instance suppresses its own echo using a per-process SERVER_ID so users don't see duplicates.

sudo apt-get install -y redis-server
sudo systemctl enable --now redis-server
redis-cli ping  # expect: PONG

Configure via REDIS_URL=redis://localhost:6379 in .env. The server logs Redis pub/sub enabled for WebSocket scaling at startup when it picks the URL up.

Production checklist:

  • Bind to localhost or the docker network; never expose Redis publicly. The default config does this; verify with ss -tlnp | grep 6379.
  • Set a password if Redis is shared across services. Use the requirepass directive, then point FlowTex at REDIS_URL=redis://:<password>@localhost:6379.
  • Persistence is unnecessary. FlowTex uses Redis purely as a pub/sub bus — no state is stored there, so you can disable RDB/AOF (save "" in redis.conf) for slightly less disk I/O.
  • Memory cap: set maxmemory 64mb with maxmemory-policy allkeys-lru. The pub/sub channel itself uses no persistent memory; this just bounds the worst case if a stuck subscriber causes a backlog.
  • Verify cross-instance broadcast after deploy: connect a WS client to instance A and another to instance B (same project), have A send an edit, observe B receives it. The bundled e2e suite exercises this with npm run e2e (test: changes broadcast crosses server instances via Redis pub/sub).
Graceful degradation: if Redis becomes unreachable at runtime, FlowTex logs Redis publish failed and continues serving — broadcasts within a single instance still work; cross-instance broadcasts silently stop. To detect this, alert on the warning log line or a Redis health probe; users won't see an error.
Sticky sessions are NOT required. Each WS connection terminates at one instance, but all instances see all broadcasts via Redis. Clients can land on any instance via simple round-robin at the load balancer.

3.2 Caddy or Nginx Recommended

A reverse proxy for TLS termination, automatic HTTPS, and serving on ports 80/443.

# Option A: Caddy (automatic HTTPS via Let's Encrypt)
sudo apt-get install -y caddy

# Option B: Nginx
sudo apt-get install -y nginx certbot python3-certbot-nginx

Example Caddy configuration (/etc/caddy/Caddyfile):

flowtex.example.com {
    reverse_proxy localhost:3001
}

Example Nginx configuration:

server {
    server_name flowtex.example.com;
    listen 443 ssl;

    ssl_certificate     /etc/letsencrypt/live/flowtex.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/flowtex.example.com/privkey.pem;

    location / {
        proxy_pass http://localhost:3001;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
WebSocket support: The Upgrade and Connection headers are essential — FlowTex uses WebSockets for real-time collaboration.
Multiple instances: the single-upstream examples above are for one app instance. To run several behind this proxy, see §4.8 — the reverse_proxy block takes a space-separated list of upstreams plus a load-balancing policy and health checks.

3.3 tex-fmt Optional

An alternative LaTeX formatter (faster than latexindent). Not available via apt; install from GitHub releases.

4. Application Setup

4.1 Install application dependencies

# Clone or copy the FlowTex source to the server
cd /opt/flowtex

# Install npm dependencies
npm install --prefix server --production
npm install --prefix client

# Build the client
cd client && npx vite build && cd ..

# Copy built assets to server
cp -r client/dist/* server/public/

4.2 Configure environment

Create .env in the project root:

# Database
PGDATABASE=flowtex
PGHOST=localhost
PGPORT=5432
PGUSER=flowtex
PGPASSWORD=your_secure_password_here

# Application
NODE_ENV=production
PORT=3001
APP_URL=https://flowtex.example.com

# Security (generate unique values!)
SESSION_SECRET=# openssl rand -hex 64
ENCRYPTION_KEY=# openssl rand -hex 32

# Email (SMTP)
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_SECURE=false
SMTP_USER=noreply@example.com
SMTP_PASS=your_smtp_password
SMTP_FROM=FlowTex <noreply@example.com>

# GitHub OAuth (optional — for GitHub sync feature)
GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=

# Redis (only needed if you run >1 FlowTex instance behind a load balancer)
# Single-instance deployments handle ~1500 concurrent users without it.
# See §3.1 in this guide for production hardening (bind, auth, no-persist).
# REDIS_URL=redis://localhost:6379

# CORS (set to your domain)
CORS_ORIGINS=https://flowtex.example.com

# Admin email
ADMIN_EMAIL=admin@example.com

# Logging (trace, debug, info, warn, error, fatal)
LOG_LEVEL=info

# DOCX import — drop image-conversion steps that shell out to
# rsvg-convert / ImageMagick / LibreOffice. Set to 1 to disable
# if you can't sandbox those binaries. Affected media is skipped.
# DISABLE_IMAGE_CONVERSION=1

# DOCX import — explicit path to the LibreOffice headless binary, used
# to convert WMF/EMF metafiles. Set only if the auto-detect (soffice on
# $PATH or in /usr/bin) doesn't find it for the FlowTex user.
# SOFFICE_BIN=/usr/bin/soffice

# TLS redirect — when NODE_ENV=production, FlowTex redirects HTTP → HTTPS
# based on X-Forwarded-Proto. Set to 1 when a reverse proxy terminates TLS
# upstream — otherwise the proxy's loopback health probe (which carries no
# X-Forwarded-Proto) gets 301'd and the instance is marked unhealthy.
# Required for any load-balanced deployment (see §4.8).
# DISABLE_TLS_REDIRECT=1

# Instance label — when running multiple instances behind a load balancer,
# set a unique value per process. It's added to every log line as
# "instance", so aggregated logs stay attributable. Optional; unset on a
# single-instance deploy. See §4.8.
# INSTANCE_ID=flowtex-1
Security: Generate unique values for SESSION_SECRET and ENCRYPTION_KEY. Never reuse these across environments. Set file permissions: chmod 600 .env. Ownership: the user that runs the FlowTex process should own .env; nothing else should be able to read it.

4.3 Start the server

For a one-off check that everything works:

node --env-file=.env server/index.js

For production, run under systemd so the service restarts on crash, on reboot, and integrates with journalctl for logs. Create /etc/systemd/system/flowtex.service:

[Unit]
Description=FlowTex collaborative LaTeX editor
After=network.target postgresql.service
Requires=postgresql.service

[Service]
Type=simple
User=flowtex
Group=flowtex
WorkingDirectory=/opt/flowtex
EnvironmentFile=/opt/flowtex/.env
ExecStart=/usr/bin/node --env-file=/opt/flowtex/.env /opt/flowtex/server/index.js
Restart=on-failure
RestartSec=5

# Hardening — harmless on most setups, defense in depth
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/flowtex/projects /opt/flowtex/git-repos /opt/flowtex/server/logs

[Install]
WantedBy=multi-user.target
# Create the dedicated user (no shell)
sudo useradd --system --home /opt/flowtex --shell /usr/sbin/nologin flowtex
sudo chown -R flowtex:flowtex /opt/flowtex

# Enable and start
sudo systemctl daemon-reload
sudo systemctl enable --now flowtex

# Tail logs
sudo journalctl -u flowtex -f

4.4 First-time setup

Open https://flowtex.example.com in a browser. The first-run wizard will prompt you to create the administrator account.

4.5 Backups

FlowTex's persistent state lives in two places: PostgreSQL and the projects/ directory.

WhatBackup with
PostgreSQL database (users, projects, file contents, sessions, snapshots, comments, tracked changes)pg_dump -Fc flowtex > flowtex.dump
/opt/flowtex/projects/ (working compilation tree — caches and PDFs, regenerable)Optional. Skipping it just means recompiling after restore.
/opt/flowtex/git-repos/ (git working copies for GitHub sync)Optional — these can be re-cloned from GitHub.
/opt/flowtex/.envBack up once, securely, off-server. SESSION_SECRET and ENCRYPTION_KEY rotation invalidates sessions and encrypted GitHub tokens.

A daily cron is sufficient:

# /etc/cron.daily/flowtex-backup
#!/bin/bash
set -e
BACKUP_DIR=/var/backups/flowtex
mkdir -p "$BACKUP_DIR"
DATE=$(date +%Y-%m-%d)
sudo -u postgres pg_dump -Fc flowtex > "$BACKUP_DIR/db-$DATE.dump"
find "$BACKUP_DIR" -name 'db-*.dump' -mtime +30 -delete

4.6 Upgrades

Upgrade procedure for a deployed instance:

cd /opt/flowtex
sudo -u flowtex git pull
sudo -u flowtex npm install --prefix server --production
sudo -u flowtex npm install --prefix client
sudo -u flowtex bash -c "cd client && npx vite build"
sudo -u flowtex cp -r client/dist/* server/public/
sudo systemctl restart flowtex

If a release adds database migrations, the server runs them automatically on start (you'll see the migration list in journalctl -u flowtex). Take a database backup before upgrading on any schema-bumping release.

4.7 Containerized Deployment (Docker Compose)

An alternative to bare-metal install. The repo ships a two-image build (a slow-changing base with Node + TeX Live, and a fast-rebuild app image) plus a hardened docker-compose.yml with Caddy + Postgres.

# One-command build (handles both images in order)
./scripts/docker-build.sh

# Configure
cp .env.example .env
# Generate SESSION_SECRET, set PGPASSWORD, DOMAIN, etc.
$EDITOR .env

# Start
docker compose up -d

# Logs
docker compose logs -f app

The compose file enables container hardening that mirrors the bare-metal systemd setup: read_only: true, cap_drop: [ALL], no-new-privileges, memory and PID caps, tmpfs for /tmp, and the runtime container drops to UID 10001 (flowtex) per the Dockerfile's USER directive.

DOCX image conversion in containers: the default base image does not include rsvg-convert / imagemagick / libreoffice. The compose file therefore sets DISABLE_IMAGE_CONVERSION=1 and DOCX images appear as placeholders. To enable, build a custom base that installs those packages plus docs/imagemagick-policy.xml and unset the env var.
Scaling out with Redis (compose): the bundled docker-compose.yml has a commented-out redis service. To run multiple app replicas, uncomment the redis block, set REDIS_URL: redis://redis:6379 on the app service, and bring up multiple replicas with docker compose up -d --scale app=3. Caddy will round-robin across them; cross-instance broadcasts cross via Redis. See §3.1 for the same details on bare metal.

4.8 Horizontal Scaling (multiple instances)

A single instance handles ~1500 concurrent connections (§3.1), so most deployments never need this. When you do outgrow one box's worth of CPU, FlowTex scales horizontally with no application changes: sessions live in PostgreSQL (any instance can serve any request) and real-time WebSocket broadcasts fan out through Redis. This section is the bare-metal equivalent of the Docker --scale note in §4.7.

Prerequisites: Redis running and reachable (§3.1), and REDIS_URL set in .env — without it each instance is an island and users on different instances won't see each other's edits.

4.8.1 Templated systemd unit

Replace the single flowtex.service from §4.3 with a template unit, /etc/systemd/system/flowtex@.service. The %i instance specifier becomes the listen port:

[Unit]
Description=FlowTex instance on port %i
After=network.target postgresql.service redis-server.service
Requires=postgresql.service

[Service]
Type=simple
User=flowtex
Group=flowtex
WorkingDirectory=/opt/flowtex
EnvironmentFile=/opt/flowtex/.env
# These three override whatever is in .env, per-instance.
# systemd applies Environment= after EnvironmentFile=, so the
# per-instance values win — remove PORT from .env to avoid confusion.
Environment=PORT=%i
Environment=INSTANCE_ID=flowtex-%i
# Required: Caddy health-probes each instance over loopback with no
# X-Forwarded-Proto. With the redirect on, the probe is 301'd and the
# instance is dropped from the pool. Caddy enforces TLS at the edge.
Environment=DISABLE_TLS_REDIRECT=1
ExecStart=/usr/bin/node --env-file=/opt/flowtex/.env /opt/flowtex/server/index.js
Restart=on-failure
RestartSec=5

# Hardening — same as the single-instance unit
NoNewPrivileges=true
PrivateTmp=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/opt/flowtex/projects /opt/flowtex/git-repos /opt/flowtex/server/logs

[Install]
WantedBy=multi-user.target
# Bring up two instances on ports 3001 and 3002
sudo systemctl daemon-reload
sudo systemctl enable --now flowtex@3001 flowtex@3002

# Status / logs for all instances at once
systemctl status 'flowtex@*'
journalctl -u 'flowtex@*' -f
Plain HTTP upstreams: in a load-balanced setup the app instances should not have server/certs/cert.pem — with no certs present each instance serves plain HTTP, and Caddy is the single TLS terminator. If you keep certs in place the instances serve HTTPS and the reverse_proxy block below must use https:// upstreams plus transport http { tls_insecure_skip_verify }.

4.8.2 Load-balancer block

Point Caddy (§3.2) at every instance. Sessions are in Postgres and broadcasts cross via Redis, so sticky sessions are not required — any client can land on any instance:

flowtex.example.com {
    reverse_proxy localhost:3001 localhost:3002 {
        # least_conn suits long-lived WebSocket connections better
        # than the default round-robin.
        lb_policy least_conn

        # Active health checks: pull a dead instance out of rotation,
        # bring it back automatically when it recovers.
        health_uri /api/health
        health_interval 10s
        health_timeout 3s
        fail_duration 10s
    }
}

Reload with sudo systemctl reload caddy. Adding or removing an instance is then: systemctl enable --now flowtex@3003, add localhost:3003 to the reverse_proxy line, reload Caddy.

4.8.3 Verify

# Both instances subscribed to the broadcast channel (expect: 2)
redis-cli pubsub numsub flowtex:ws

# Caddy sees both upstreams healthy
journalctl -u caddy | grep "health_checker"   # expect "host is up" for each

# Logs are attributable — every line carries its instance label
journalctl -u 'flowtex@*' -o cat | grep -o '"instance":"[^"]*"' | sort | uniq -c

For an end-to-end check of cross-instance broadcast, run the bundled e2e test described in §3.1.

To confirm the balancer actually spreads traffic, drive load through it with the bundled harness — --target points it at the proxy instead of one instance, --origin sets the Origin header to match APP_URL:

node --env-file=.env server/loadtest.js --users 150 --duration 40 \
  --target https://flowtex.example.com --origin https://flowtex.example.com

# While it runs, connections should split roughly evenly:
ss -tnp | grep -c ':3001'   # instance 1's share
ss -tnp | grep -c ':3002'   # instance 2's share

5. One-Shot Provisioner

For a fresh Ubuntu 22.04/24.04 VPS (e.g. a Contabo Cloud VPS), the repo ships scripts/provision-vps.sh — it does everything in sections 2–4 in one run: installs all packages, creates the database, clones and builds the app, generates secrets and a production .env, installs a hardened systemd service behind Caddy with automatic HTTPS, opens the firewall, and starts it.

Prerequisite: a DNS A/AAAA record for your domain must already point at the VPS — Caddy fetches the TLS certificate on first start.
# On the fresh VPS, as root:
curl -fsSL https://raw.githubusercontent.com/stolucc/flowtex/main/scripts/provision-vps.sh -o provision-vps.sh
DOMAIN=flowtex.example.com ADMIN_EMAIL=you@example.com bash provision-vps.sh

Optional env vars: REPO_URL, BRANCH, APP_DIR (default /opt/flowtex), APP_USER (default flowtex), WITH_REDIS (default 0 — only needed for multi-instance, see §4.8), WITH_DOCX (default 1 — the DOCX-import image toolchain).

Re-running the script pulls the latest BRANCH, rebuilds, and restarts — so it doubles as the upgrade path. An existing .env is left untouched, so secrets are never rotated by accident.

7. Where to Look When Things Go Wrong

SymptomWhere to look
Service won't startsudo journalctl -u flowtex -n 200 — usually a missing env var or a DB connection issue
WebSocket fails (no live cursors / collab)Reverse proxy must forward Upgrade + Connection: upgrade headers (see Caddyfile / Nginx examples above)
Login redirects foreverNODE_ENV=production sets secure cookies — ensure traffic actually reaches the server over HTTPS, or your reverse proxy sets X-Forwarded-Proto: https
Compilation hangs / OOMEach compile uses ~500 MB. Check free -h during a compile; raise RAM or limit concurrency. texlive-full packages the whole TeX universe — texlive-base + selective packages can shrink memory pressure but at the cost of more "missing package" errors.
DOCX import drops imagesCheck that rsvg-convert, convert, and soffice are on $PATH for the FlowTex user (run sudo -u flowtex which rsvg-convert convert soffice). If you've set DISABLE_IMAGE_CONVERSION=1 deliberately, this is expected.
Sessions / GitHub tokens vanish after restartYou changed SESSION_SECRET or ENCRYPTION_KEY. Don't rotate these without a re-encryption migration plan.
